# Протокол клиент–сервер Cloute

Версия протокола: **1**. Этот документ — источник истины: сервер (`internal/transport/ws`) и клиент (`web/src/sync`) реализуют то, что здесь описано.

## Транспорт

- WebSocket, эндпоинт `GET /ws`. Один документ на одно соединение.
- Каждое сообщение — один текстовый фрейм с JSON-объектом. Бинарные фреймы запрещены.
- Максимальный размер сообщения от клиента — **1 MiB**. Клиент разбивает большие правки на несколько сообщений `ops` (веб-клиент — по 1000 операций).
- В каждом сообщении есть поле `v` — версия протокола (сейчас `1`) и поле `type`.
- Сервер принимает соединение, только если заголовок `Origin` отсутствует или его хост совпадает с `Host` запроса (защита от cross-site WebSocket hijacking).
- **Аутентификация** — cookie сессии `cloute_session` (см. `api/http.md`), которую браузер сам отправляет при открытии WebSocket. Без действительной сессии сервер отвечает `error{code: "unauthorized"}` и закрывает соединение.
- **Доступ** — роль пользователя в документе читается из БД при подключении. Если ссылку, через которую пользователь получил роль, отзывают, сервер закрывает его соединения (см. коды закрытия), и при переподключении роль читается заново. Повышение роли новой ссылкой действует со следующего подключения.

## Идентификаторы и операции

ID символа — массив `[lamport, replica]`:

- `lamport` — целое `1 … 2^53−1` (верхняя граница — точность `number` в JavaScript);
- `replica` — целое `1 … 2^32−1`, выдаётся сервером в `welcome`, уникален в пределах документа;
- `[0, 0]` — виртуальная голова документа: вставка с `after: [0, 0]` попадает в начало.

Операции (тот же формат, что в тест-векторах `testdata/crdt/`):

```json
{"type": "insert", "id": [7, 2], "after": [5, 1], "char": "ж"}
{"type": "delete", "id": [5, 1]}
```

- `char` — ровно одна кодовая точка Unicode, не одиночный суррогат. Символ вне BMP (`"👋"`) — это один `char`, хотя в UTF-16 он занимает две кодовые единицы.
- У `insert` обязательно `id.lamport > after.lamport`.

## Сообщения

### Клиент → сервер

**`hello`** — первое сообщение после открытия соединения; должно прийти в течение 10 с.

```json
{"v": 1, "type": "hello", "docId": "report-2026"}
```

`docId` — 1–64 символа из `[A-Za-z0-9_-]`. Документы создаются через HTTP API; если документа нет или у пользователя нет в нём роли, ответ — `error{code: "forbidden"}` (одинаковый в обоих случаях).

После переподключения клиент продолжает прежнюю сессию:

```json
{"v": 1, "type": "hello", "docId": "report-2026", "replica": 2, "lastSeq": 42,
 "pending": [{"type": "insert", "id": [17, 2], "after": [16, 2], "char": "ы"}]}
```

| Поле | Смысл |
|---|---|
| `replica` | Номер реплики, полученный в прошлом `welcome`. Сервер продолжает сессию с ним, поэтому операции, созданные офлайн, сохраняют свои ID. Номер выдаётся конкретному пользователю: номер, который не выдавался этому пользователю в этом документе, — ошибка `bad_request`. Соединение этой же реплики, которое ещё считается живым, вытесняется (закрывается с кодом 1000). |
| `lastSeq` | Последний `seq`, известный клиенту. Если клиент отстал не более чем на 1000 операций, `welcome` присылает только недостающие операции, иначе — снапшот. |
| `pending` | Операции клиента, не подтверждённые `ack`: и отправленные, и созданные офлайн, в порядке создания, не более 1000 (остальные клиент шлёт обычными `ops` после `welcome`). Сервер применяет их сразу после `welcome` и подтверждает одним `ack`. |

**`ops`** — операции, созданные локальными правками клиента. Непустой список.

```json
{"v": 1, "type": "ops", "ops": [{"type": "insert", "id": [3, 2], "after": [0, 0], "char": "a"}]}
```

Сервер принимает операцию, только если:

- роль клиента — `owner` или `editor` (иначе `forbidden`, см. `welcome`);
- `insert` создаёт ID со своим `replica` клиента;
- символ, на который ссылается операция (`after` у `insert`, `id` у `delete`), уже есть на сервере. Клиент ссылается только на символы, которые получил от сервера или сам отправил раньше по этому же соединению, поэтому у правильного клиента это всегда так;
- операция корректна для CRDT (`lamport > after.lamport`, допустимый `char`, нет другой вставки с тем же ID).

**`presence`** — свой курсор или выделение. Отправлять может любая роль; веб-клиент шлёт не чаще 10 раз в секунду.

```json
{"v": 1, "type": "presence", "cursor": {"anchor": [5, 2], "head": [9, 2]}}
```

Каждый конец выделения — позиция **сразу после символа** с этим ID (`[0, 0]` — начало текста), удалённого или нет. Позиция по ID, а не по индексу, не сдвигается, когда другие правят текст перед ней. Курсор на неизвестный серверу символ молча игнорируется. Курсоры не хранятся и не получают `seq`.

**`comment`** — комментарий к символам `from … to` включительно (в порядке документа).

```json
{"v": 1, "type": "comment", "from": [12, 2], "to": [17, 2], "text": "раскрыть подробнее"}
```

Только `owner`, `editor`, `commenter` (иначе `forbidden`). `text` — 1–2000 символов после обрезки пробелов; `from` и `to` — известные серверу символы, `from` не позже `to` (иначе `invalid_op`). Комментарии идут по тому же соединению, что и `ops`, поэтому комментарий к только что напечатанному тексту не может обогнать сами символы.

**`resolve`** — закрыть комментарий.

```json
{"v": 1, "type": "resolve", "id": 7}
```

Может автор комментария или `owner`/`editor` (иначе `forbidden`). Закрытие уже закрытого или несуществующего комментария ничего не делает: двое могли нажать «закрыть» одновременно.

### Сервер → клиент

**`welcome`** — ответ на `hello`, всегда первое сообщение от сервера. Ровно одна из двух форм:

```json
{"v": 1, "type": "welcome", "replica": 2, "role": "editor", "seq": 42, "snapshot": {"chars": [ ... ]}}
{"v": 1, "type": "welcome", "replica": 2, "role": "editor", "seq": 47, "ops": [ ... ]}
```

- `role` — роль пользователя в документе: `owner`, `editor`, `commenter` или `viewer`. Отправлять `ops` (и непустой `hello.pending`) могут только `owner` и `editor`; от остальных сервер ничего не применяет, отвечает `error{code: "forbidden"}` и закрывает соединение.
- `replica` — номер реплики клиента для новых ID (тот же, что в `hello.replica`, если он был). Сервер резервирует номера в БД, поэтому они не повторяются и после перезапуска сервера.
- `seq` — номер последней операции документа на момент `welcome` (без `hello.pending`).
- `snapshot` — состояние документа после операций `1 … seq` (формат ниже). Клиент строит реплику из снапшота и **заново применяет к ней свои неподтверждённые операции**: в снапшоте их ещё нет (или уже есть — тогда повторное применение ничего не меняет).
- `ops` — догон: операции `lastSeq+1 … seq` для клиента, который прислал `lastSeq` и сохранил свою реплику. Список может быть пустым (`[]`). Среди них могут оказаться собственные операции клиента, чей `ack` потерялся при разрыве, — для CRDT их повторное применение ничего не меняет.

### Снапшот

```json
{"chars": [
  {"id": [1, 1], "after": [0, 0], "char": "A", "deleted": true},
  {"id": [2, 1], "after": [1, 1], "char": "B"}
]}
```

- `chars` — **все** символы документа, включая удалённые (tombstones), в порядке документа.
- `deleted` присутствует и равно `true` только у удалённых символов.
- `after` каждого символа встречается в списке раньше него (или это `[0, 0]`); иначе снапшот некорректен.
- Пример и общий тест Go/TS: `testdata/protocol/snapshot.json`.

Тот же JSON хранится в БД (`doc_snapshots.state`), операции — в формате из раздела выше (`doc_ops.op`).

**`ack`** — пачка `ops` клиента (или `hello.pending`) принята целиком и записана в БД.

```json
{"v": 1, "type": "ack", "seq": 45}
```

- На **каждое** сообщение `ops` и на непустой `hello.pending` приходит ровно один `ack`, в том же порядке. Клиент ведёт очередь отправленных пачек и снимает по одной на каждый `ack`.
- `seq` — номер последней операции документа после этой пачки.
- Операции, которые у сервера уже есть (клиент переотправил их, потому что `ack` потерялся при разрыве), пропускаются: в лог они второй раз не попадают и другим клиентам не рассылаются. Пачка из одних таких операций всё равно получает `ack`.
- Сервер **не** присылает клиенту его собственные операции обратно.

**`ops`** — операции, принятые от других клиентов. Откат к версии (`api/http.md`) приходит так же — обычными операциями, во всех подключённых клиентах, включая того, кто откатывал.

```json
{"v": 1, "type": "ops", "seq": 47, "ops": [ ... ]}
```

Операции пачки имеют номера `seq − len(ops) + 1 … seq`.

**`comments`** — все незакрытые комментарии; приходит сразу после `welcome`, если они есть. Клиент сбрасывает свой список комментариев на каждом `welcome`.

```json
{"v": 1, "type": "comments", "comments": [{"id": 7, "from": [12, 2], "to": [17, 2], "text": "…", "author": {"id": 3, "name": "Преподаватель"}, "createdAt": "2026-10-17T00:30:00Z", "resolved": false}]}
```

**`comment`** — новый (`resolved: false`) или закрытый (`resolved: true`) комментарий, всем клиентам документа, включая автора; в том же формате, что элемент `comments`.

Фрагмент комментария на экране — видимые символы между `from` и `to` в порядке документа: вставки внутри него расширяют фрагмент, вставки и удаления снаружи его не сдвигают; если весь текст фрагмента удалён, фрагмент пуст (комментарий остаётся).

**`presence`** — курсор другого участника; после `welcome` приходят курсоры всех, кто уже здесь (если есть). `cursor: null` — участник ушёл. Клиент сбрасывает курсоры на каждом `welcome` и при разрыве соединения.

```json
{"v": 1, "type": "presence", "replica": 3, "user": {"id": 3, "name": "Преподаватель"}, "cursor": {"anchor": [5, 2], "head": [9, 2]}}
{"v": 1, "type": "presence", "replica": 3, "cursor": null}
```

**`error`** — ошибка клиента; сразу после неё сервер закрывает соединение.

```json
{"v": 1, "type": "error", "code": "invalid_op", "message": "..."}
```

| `code` | Когда |
|---|---|
| `unsupported_version` | `v` не равно 1 |
| `bad_request` | битый JSON, неизвестный `type`, первое сообщение не `hello`, повторный `hello`, неверный `docId`, `hello.replica`, который не выдавался |
| `invalid_op` | операция не прошла проверку; операции пачки до неё приняты и разосланы, но `ack` не отправляется |
| `unauthorized` | нет действительной сессии; клиент не переподключается, а просит войти |
| `forbidden` | нет роли в документе, роль не позволяет править или комментировать, чужой комментарий закрывает не редактор; клиент не переподключается |

## Порядок и номера `seq`

- Сервер присваивает каждой принятой операции номер `seq`: 1, 2, 3, … без пропусков, в порядке приёма.
- Клиент получает каждый номер ровно один раз: либо в `welcome` (через снапшот), либо в `ack` (свои операции), либо в `ops` (чужие). Сообщения приходят в порядке возрастания `seq`.
- Операция получает номер, рассылается и подтверждается только после записи в БД.
- Поэтому максимальный увиденный `seq` — это точная граница того, что клиент знает о документе; его клиент передаёт в `hello.lastSeq` после переподключения.

## Офлайн и переподключение

1. Связь пропала (закрытие сокета или событие `offline` браузера). Клиент продолжает редактировать свою реплику; операции копятся в очереди вместе с отправленными, но не подтверждёнными.
2. Клиент переподключается (раз в секунду или сразу по событию `online`) и шлёт `hello{replica, lastSeq, pending}`.
3. Сервер отвечает `welcome` (догон или снапшот), применяет `pending`, присылает `ack` и рассылает новые операции остальным.
4. Если сервер отвечает `error` (например, `lastSeq` больше его `seq` — сервер потерял данные, которые клиент видел, и `pending` ссылается на них), состояние клиента принять уже нельзя: клиент сбрасывает реплику и очередь и начинает заново с `hello{docId}`.

Курсоры и комментарии офлайн не копятся: пока связи нет, форма комментария недоступна, а свой курсор клиент отправляет заново после `welcome`.

Неподтверждённые операции хранятся только в памяти вкладки: закрытие вкладки офлайн их теряет (клиент предупреждает об этом через `beforeunload`).

## Проверка живости

Сервер раз в 30 с шлёт WebSocket ping. Если pong не пришёл за 10 с, соединение закрывается без handshake: клиент считается отключённым, его место освобождается.

## Закрытие соединения

| Код WebSocket | Причина |
|---|---|
| 1000 Normal Closure | обычное закрытие; соединение, вытесненное новым подключением той же реплики; роль пользователя изменилась — отозвана ссылка доступа (reason `access changed`), клиент переподключается и получает новую роль или `forbidden` |
| 1001 Going Away | сервер останавливается |
| 1008 Policy Violation | ошибка протокола (перед закрытием отправлен `error`) |
| 1009 Message Too Big | сообщение больше 1 MiB |
| 1011 Internal Error | ошибка хранилища: документ не удалось загрузить или записать |
| 1013 Try Again Later | клиент не успевает читать: его очередь исходящих сообщений (256) переполнилась |

После любого закрытия клиент переподключается с тем же `replica` (см. «Офлайн и переподключение»).
